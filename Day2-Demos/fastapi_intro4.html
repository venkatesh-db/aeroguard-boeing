An API is a service counter

An app (the client) sends a request to your API. FastAPI finds the right Python function, runs it and sends back a response, usually JSON. Like a stores counter in the hangar: you ask for a part, they check and hand it over.

💡 The four everyday "verbs": GET read · POST create · PUT update · DELETE remove. Status codes: 200 OK · 201 Created · 404 Not found · 422 bad data · 500 server error.

Routes: URL + method → Python function

A decorator like @app.get("/defects/{defect_id}") connects a URL to a function. Type a URL and watch FastAPI find the route.

💡 {defect_id} is a path parameter. FastAPI pulls it out of the URL and, because of : int, converts it to a number for you.

Pydantic models: a form with rules

A Pydantic model describes the shape of the data. FastAPI checks every request against it. Bad data is rejected with a clear 422 error before your code even runs.
💡 Request model (DefectIn) = what clients must send. Response model (DefectOut) = what you send back. Fields not in it, like internal_notes, are automatically hidden.

.env: keep settings and secrets out of your code

API keys and passwords must never be typed into code or pushed to Git. Put them in a .env file, load them with pydantic-settings, and list .env in .gitignore.
